# Local drafts

Read when: preparing durable offline previews without sending, or inspecting retained revisions and document/image/voice snapshots.

`draft create/show/list/update/discard/cleanup` prepares only local records in the selected account's existing `wacli.db` (introduced in schema 30; current schema 31). There is no `draft send`, automatic replay, download, transcription, export command or automatic garbage collection. No draft command opens/connects a WhatsApp client. A preview does not verify that a recipient exists remotely. The separate [outbound action](outbound.md) dispatches an explicitly selected immutable revision/hash with a retained idempotency key.

A draft write returning `store_locked` (exit 4) advises waiting for the current writer to finish, then inspecting drafts and the intended result before explicitly requesting the action again. This error does not establish whether another writer created a draft or an earlier request completed; publication and uncertain-result errors retain their own guidance.

## Commands

Selection preserves the existing `--account`, `--store`, environment and default rules. The resolved store is fixed once before LOCK/IPC and appears as `account.store_ref` in agent JSON and draft write/show/list JSON. Create/update require exactly one locally persisted own PN identity; missing, ambiguous or unreadable public session identity returns exit 4, with no session creation or connection. Show/list/discard/cleanup use the frozen record even without a current session.

```bash
wacli --account personal draft create --to +15550000002 --message 'literal text' --agent
wacli --account personal draft show DRAFT_ID --revision REVISION_ID --agent --detail full
wacli --account personal draft list --agent --limit 20
wacli --account personal draft update DRAFT_ID --if-revision CURRENT_REVISION --to 15550000002@s.whatsapp.net --message 'complete replacement' --agent
wacli --account personal draft discard DRAFT_ID --if-revision CURRENT_REVISION --agent
```

IDs are random lowercase 32-character hex strings. A draft's current pointer changes on update; every revision remains immutable and individually retrievable. Update supplies complete input, including recipient, rather than a patch. Both update and discard compare `--if-revision` at the writer; conflicts use exit 1. Discard marks the draft abandoned, keeps its current pointer and retains every revision/snapshot. It neither requires the current own identity nor deletes bytes. To inspect abandoned drafts, use `list --include-discarded`.

Update and discard keep the mutable draft record's timestamps nondecreasing, even when the system clock moves backwards. `created_at` stays fixed; `updated_at` never falls below the retained creation or update time, and discard uses that same effective time for `discarded_at`. Returned records contain the persisted values. Revision timestamps and payload hashes remain unchanged, so an immutable revision's timestamp can precede the draft's creation or latest update after a clock adjustment. Discard also checks the head and update timestamp used to calculate its result; a concurrent change returns a conflict. This prevents new clock-related cleanup failures without a migration or automatic repair of previously inconsistent records. An already discarded record with timestamps preceding its creation can still fail cleanup validation with `store_error`.

List reads stored summaries, not full payloads or media. Defaults are 20, bounds 1–200. Agent `--cursor` is a strict canonical versioned token, capped at 16 KiB and scoped to store and inclusion of discarded drafts. Ordering is immutable `(created_at, id)`; size/detail can change between pages. Status filtering is live: discarded drafts disappear on subsequent pages. Cursors are neither credentials nor authorization.

## Recipient and payload

`--to` accepts an explicit formatted PN phone (7–15 digits), numeric PN/LID JID, or numeric group JID. Device suffixes are syntactically normalized. Names are not accepted: first use `contacts search/resolve` or `chats list` and pass the resulting JID. Broadcasts, status, newsletters and other servers are rejected. Mentions accept only explicit users, up to 200 input entries; canonical duplicates merge and ordering is deterministic. Locally established self targets are rejected. Unknown self status remains unknown.

Each revision freezes the raw requested target, normalized requested JID, canonical recipient, observed PN/LID pair, display name and public own PN/LID identity. An unmapped LID remains a LID with an empty PN. Public mapping query errors are errors, not absence; no phone is inferred from LID digits. Stores/accounts remain separate. A later map/name change does not rewrite a preview. Future sending must compare relevant identity facts and require a new revision for relevant changes.

Choose exactly one variant:

- Text: `--message TEXT` or `--message-file PATH|-`. UTF-8, newline and literal backslashes are preserved exactly, without trim, NFC normalization or automatic escape decoding. File/stdin reads are bounded while streaming. `--mention USER` is repeatable.
- Fixed document: `--file PATH [--filename NAME] [--mime MIME] [--caption TEXT]`. The display filename defaults to the source basename. MIME defaults to sniffing the first bytes from the same snapshot read; an explicit concrete MIME override is normalized. No automatic image/audio/video selection.
- Static image: `--image PATH [--caption TEXT]`. JPEG/PNG only, selected explicitly and validated from captured bytes. It is exclusive of text/contact/document input and document `--filename`/`--mime` options, including explicitly empty flags. A PNG containing APNG animation chunks is rejected; GIF/WebP/HEIC/SVG and other formats are unsupported. Literal caption and the existing frozen textual quote policy are preserved.
- Voice PTT: `--voice PATH [--reply-to ID]`. Complete Ogg/Opus in the strict local profile below. No caption, filename, MIME override, mentions, waveform, duration probe or conversion. It is exclusive by flag presence, including empty flags, of all other content variants and their options.
- One explicit contact: `--contact-name NAME --contact-phone PN`. The exact display name and normalized explicit PN number appear in the DTO. Deterministic textual vCard 3 uses CRLF, escapes backslash/newline/semicolon/comma in name fields and confines the phone to validated digits. Adversarial names cannot inject properties. WhatsApp compatibility has not been tested live.

Text/document/image may use `--reply-to MESSAGE_ID` for an existing local textual message in this exact chat or its verified alias. The revision freezes chat+real ID, sender identity, `from_me` and actual text. Missing/unknown sender, unavailable/purged/revoked/deleted text, unsupported media/buttons/reactions and divergent records with the same ID in verified aliases are rejected. Incoming DM quotes must match the peer through shared observed PN/LID facts; contradictory pairs or an observed own sender with `from_me=false` are rejected. Outgoing quotes must match own identity. Group quotes allow any valid user sender without claiming membership. Unmapped distinct identities cannot prove peer equality. All checks precede snapshot/commit. No arbitrary quote input or remote lookup exists. Later message edits do not replace the frozen quote.

Whitespace-only quotes remain invalid. Valid quotes retain their stored text bytes; verified aliases differing only in leading/trailing whitespace are still divergent. New preparations hash the newly frozen raw quote; retained revisions, hashes and outbound bindings are not rewritten.

Unsupported quote content (media, buttons or reactions) uses fixed local guidance with `invalid_arguments` (exit 2), even when a caption and sender are present. Inspect the local message with `messages show --chat CHAT_JID --id MESSAGE_ID --agent --detail full`; choose a supported text quote or explicitly prepare complete create/update input without `--reply-to`. No quote is removed automatically. Unavailable/revoked/deleted/purged content in either verified alias takes precedence and keeps the existing generic refusal; unsupported guidance makes no claim about sender validity.

CLI limits are 64 KiB per field, 256 KiB canonical payload (including JSON escaping), 200 mentions, and 100 MiB per file. Escaped vCard and quote fields also obey limits. These are CLI quotas, not verified WhatsApp limits. Effective defaults explicitly disable link preview, ephemeral mode/expiration and self targeting.

The payload hash is SHA-256 over the UTF-8 prefix `wacli-draft-payload-v1`, one NUL byte, then deterministic canonical struct JSON with effective defaults, identity, canonical recipient, content, mentions and frozen quote. Revision IDs, timestamps, requested-input spelling and review/display metadata are outside this hash. Internal input rejects ambiguous unions, unknown/duplicate fields, malformed UTF-8, noncanonical encoding and nonfinite values. Hash equality neither authorizes sending nor proves a person read the preview.

## Preview and snapshot bytes

Agent output preserves contract v1 and `source=local`, unknown freshness/completeness, and compact/full envelope caps (1 MiB / 8 MiB). Legacy `--json` includes the selected account and draft; `--full` selects full draft detail without agent mode. Compact cuts selected content/name fields at 512 Unicode code points and reports `truncated_fields`; identifiers, mentions, mappings, defaults and digest/size stay complete. Compact can suffice when all relevant fields are present; use full to recover truncated fields needed for review. Compact is not guaranteed to encode fewer bytes than full: truncation markers and recovery guidance can outweigh the omitted text near the cutoff. No read/approved state is recorded.

When long text already requires complete review, request full detail directly to avoid a second query:

```bash
wacli --account personal draft create --to 15550000002@s.whatsapp.net --message-file ./long-text.txt --agent --detail full
```

For a single draft revision, `data.recovery` is the canonical complete guidance in agent output. When guidance is present, `meta.recovery` contains only `See data.recovery.`; neither field is emitted for untruncated text/contact revisions. Text/contact truncation guidance requests the exact full revision without document advice. Document guidance always requires separate byte inspection; compact also directs full recovery for the expected snapshot path and any truncated fields. Legacy JSON keeps complete guidance in `data.draft.recovery`, and human output keeps it in the displayed draft's `recovery`. List retains its separate summary-only guidance in `meta.recovery`.

A document or image revision reports digest, size and `verified_at_create`, describing only the creation-time read. Full additionally exposes `document.snapshot_path` or `image.snapshot_path`, derived from the **currently selected fixed store + validated revision ID**, at `draft-media/REVISION_ID.blob`. It never exposes the original import path or internal metadata. Inspect it explicitly with appropriate local tools:

```bash
wacli --account personal draft show DRAFT_ID --revision REVISION_ID --agent --detail full
# Use the returned document.snapshot_path for separate local byte inspection.
```

This deliberate path exception is restricted to document/image draft detail. The path is an expected location, can be absent/altered and follows store relocation. Neither full nor compact certifies current integrity or approval. **Show/list never open or stat media**, including old revisions after update/discard. Outbound dispatch revalidates size/digest on the same bytes actually used for sending; it does not reload current quote text.

Snapshot creation rechecks `WACLI_MEDIA_ROOTS` in the process opening the source. It validates the opened FD as regular, then copies in cancellable 32 KiB chunks with a 100 MiB+1 limit, computing digest, size and MIME sniff on the copied bytes. Opening-time stat is not a path-immutability guarantee: concurrent writes can affect the captured sequence; the retained bytes/digest describe that sequence. Cancellation is checked between reads/writes, not an interrupt guarantee for blocked filesystem syscalls.

Each document/image revision gets its own exclusive managed file (0700 directory / 0600 files on Unix); no global dedupe or content-addressable cache. Publication uses a no-overwrite hard link, then directory sync before the SQLite revision commit. A filesystem must support hard links. Windows skips unsupported directory sync; this is not a power-loss transaction spanning filesystem and DB.

Publication/commit uncertainty preserves artifacts. A crash after publication and before DB commit can leave an unreferenced blob; no unknown artifact is deleted on recovery. Only the known unpublished temporary file belonging to the current failed attempt is eligible for cleanup by snapshot creation. A synthetic Linux streaming+SHA benchmark (100 MiB, 3 iterations, i9-13950HX) measured approximately 86 ms / 1.2 GB/s and 33 KiB allocated per iteration; it excludes disk copying and fsync and is not a filesystem performance guarantee. Retention grows after updates/discards and consumes one full document copy per revision. Explicit byte retention cleanup is described below; no automatic GC or orphan purge exists.

## Static image preparation and dispatch

Image drafts use the existing schema 31 and payload/hash v1. Existing text/document/contact canonical bytes and hashes stay identical. Images freeze their effective MIME, dimensions, size, digest, literal caption and the exact JPEG thumbnail used by dispatch. The thumbnail stays in the private payload; public compact/full output exposes only `thumbnail_bytes` and `thumbnail_sha256`, alongside image metadata. No blob/base64 or original source path is exposed. Full additionally returns the derived expected snapshot path for separate visual inspection. Neither output level records human approval or certifies current bytes; show/list never open or stat the snapshot.

Preparation validates JPEG/PNG configuration before a complete decode, with positive representable dimensions and a **40 million pixel** ceiling checked without overflowing arithmetic. PNG animation chunks are rejected even if the standard decoder could display their default image. The 100 MiB file and 256 KiB encoded payload quotas still apply, including the thumbnail and quote. Original bytes are captured once and retained unchanged. Decode and thumbnail generation use that captured buffer; the thumbnail is generated once during preparation, at up to 96 pixels with JPEG quality 75. These limits do not bound total RSS: captured bytes, decoded pixels, SQLite and SDK buffers add memory. Cancellation is checked around decode and in streaming chunks; it cannot interrupt an individual image decoder call or filesystem syscall.

No conversion, EXIF stripping or orientation correction occurs. JPEG dimensions and thumbnail use the encoded pixel orientation, ignoring EXIF orientation; a viewing client may render the original differently. The original PNG retains transparency. The thumbnail keeps the existing legacy alpha rendering rather than introducing new compositing behavior; JPEG cannot represent transparency, so it may differ visually from the original. Inspect the original separately.

Create/update with image input use local draft request v2, without a legacy `File` field. Text/document/contact/discard requests remain v1; voice create/update use v3 below. v1 with image and v2 without valid image create/update are refused before IO. Upgrade CLI and owner together: a base owner rejects v2 and cannot prepare it as a document. Because that owner's request echo omits the new field, its refusal can surface as `local_write_uncertain`; inspect exact IDs, never downgrade or replay automatically. An old client rejects `--image`; an old owner cannot decode a stored image for outbound dispatch. Unknown/mismatched/lost replies remain uncertain without legacy or standalone fallback.

Explicit `outbound send D --revision R --expect-hash H --key K` uses the existing executor with MediaImage/ImageMessage. Before connecting/uploading, it revalidates managed snapshot size/digest on the exact upload buffer and checks frozen MIME/dimensions against its header/config. It uses only frozen metadata/thumbnail/quote, without reopening the import source, decoding pixels again or rebuilding the thumbnail. Idempotency, SDK same-ID retries, readonly guards, ACK/history warnings and receipt certainty retain their existing contracts. Generic audio remains outside immutable draft support. Voice/PTT uses the separate explicit contract below.

Image bytes remain retained after update/discard. Document cleanup reports image revisions as `non_document`, including discarded unreferenced images; it cannot unlink them. There is no automatic GC or image cleanup mode.

## Explicit document byte cleanup

```bash
wacli --account personal --agent --read-only draft cleanup preview DRAFT_ID --limit 20
wacli --account personal --agent draft cleanup preview DRAFT_ID --cursor TOKEN --detail full
wacli --account personal --agent draft cleanup apply DRAFT_ID --revision REVISION_ID --if-revision CURRENT_HEAD --expect-hash COMPLETE_PAYLOAD_SHA256
```

Preview is the dry-run. Apply selects exactly one revision, including a sole discarded head; there is no bulk, age, path, force, orphan or automatic cleanup mode. All three selection flags are required. `--read-only` / `WACLI_READONLY=1` reject apply before opening the archive, LOCK or socket. Both commands stay `source=local`; neither needs current session identity. Preview `data={draft_id,state,expected_head_revision_id,revisions,page_counts,has_more,next_cursor}` includes each revision's full hash, ordinal, kind, eligibility, outbound-reference count and creation-time document bytes/digest. Full adds only a derived expected `snapshot_path` for documents. Agent `meta.page` repeats page navigation; `--cursor` is agent-only. Legacy output is JSON (preview uses the same DTO, `--full` adds paths). Apply returns the same compact/full DTO: `{draft_id,revision_id,hash,effect,outcome,directory_sync,removed_bytes}`.

Cleanup eligibility concerns only document bytes of a **discarded** draft, including its head or sole revision, provided **no outbound operation references that revision**. Every phase/result protects the bytes, including pending, uncertain, rejected and not-dispatched attempts. Active drafts, non-document revisions and outbound references have explicit noneligible reasons. All draft/revision rows, immutable payloads/reviews/hashes, head pointers, keys, operations and receipt evidence remain retained. There is no migration, new index, expiry policy, automatic execution or cleanup of unknown/orphan/temporary files. Append-only catalogue growth remains a limit; this does not compact the whole archive.

`draft cleanup preview D` reads one bounded readonly catalogue snapshot without snapshot reads/stats, LOCK, session access, migrations or permission normalization. It requires the current compatible archive; old/missing stores are not initialized or upgraded. Pages use the existing `(draft_id,revision_no)` index, default CLI size is 20 with bounds 1–200, and canonical versioned cursors bind store, draft and policy. Subsequent pages are new snapshots; size/detail may change. Corrupt selected payloads or draft/head records fail rather than becoming eligible. Complete hashes and creation-time document sizes are returned without content. Counts partition only the returned page; eligible bytes are historical metadata, not evidence of presence, current integrity or recoverable disk space. One reference query accepts at most 200 revision IDs, retaining only page-sized counts in Go; SQLite may scan the outbound catalogue. Ordinary readonly WAL/SHM bookkeeping and filesystem read-atime limitations still apply.

Synthetic Linux measurements (Go 1.27.1, i9-13950HX, three iterations, 1 KiB document captions) were approximately 8–9 ms per 20-revision preview and 54–57 ms per 200-revision preview, with zero versus 1,000 operations. Cumulative Go allocations were approximately 0.7 MB and 6.7 MB per page respectively; these are not peak-memory/RSS bounds. Streaming verification of local 1 MiB and 100 MiB fixture files allocated approximately 33 KiB per iteration; the 100 MiB read took approximately 109 ms. A separate three-iteration single-revision FULL-guard benchmark measured approximately 3.6 ms and 20 KiB allocated per call. Measurements exclude fixture setup, unlink and directory sync; preview/streaming measurements also exclude FULL commits. They do not predict other storage or concurrent workloads. Preview retains a bounded head/current revision plus its page; large payloads and SQLite native work remain relevant costs.

`draft cleanup apply D --revision R --if-revision HEAD --expect-hash HASH` retains the existing store LOCK/owner slot through completion. It validates D/R/expected head/hash and readonly policy before filesystem effects, never opens a WA/session client and never uses send pacing. A single path is derived strictly from the selected revision under the selected store's `os.Root`. Existing regular file descriptors, directory/file identity, size and SHA-256 are checked, streaming with a 32 KiB buffer and the existing 100 MiB content bound. No source/import path is reused. Symlinks, unexpected types, changed files, incompatible metadata and arbitrary paths are rejected.

Before unlink, a short leased FULL transaction revalidates discard, expected head, hash and absence of outbound references, and effectively advances the existing `drafts.updated_at`, with overflow rejection. This real write reaffirms a preceding NORMAL discard before the filesystem effect. Revisions and their creation-time verification stay immutable; `updated_at` is **not a cleanup journal or proof of removal**. Commit, rollback/restoration failures or lost commit confirmation never authorize unlink. After confirmed commit/restoration, cancellation and file identity are rechecked while exclusion remains held. Discarded state prevents cooperating writers from updating or reserving a new operation; already-bound operations always protect their revision.

The result distinguishes this call's unlink effect (`not_removed`, `removed`, `unknown`) from its overall outcome. Prior absence is `already_absent_unknown`, with zero bytes removed in this call and no inferred cause. An unlink error has unknown effect and a nullable byte count; successful unlink followed by directory-sync failure retains the known removed effect but reports uncertainty. Cancellation before unlink preserves bytes; cancellation after unlink does not skip directory sync and cannot undo removal. Byte counts describe logical content, not freed blocks: hard links and open descriptors can retain storage. No uncertain result is replayed automatically.

The standalone command first opens a readonly compatible archive to preflight the exact catalogue selection, then acquires the existing writer LOCK and opens writable; it never initializes/upgrades an old or missing archive merely to clean bytes. If the LOCK belongs to an existing owner, only the distinct typed `local_draft_cleanup` kind uses the same socket and serialized operation slot, without WA or pacing. The owner rechecks writable policy, exact store and selection; exclusion lasts through directory sync. One caller deadline covers queueing and work, with no application retry. Filesystem calls are not strictly interruptible. The canonical request/reply is a bounded 16 KiB newline frame; a hash binds version/store/D/R/head/hash on the existing connection, without a database replay key. Old/untyped owners, wrong correlation, timeout or lost response after submission report unknown effect, without fallback or repeated execution. Owner shutdown retains existing handler draining before releasing DB/LOCK.

Cleanup errors use their own codes and optional `error.cleanup` in agent or legacy `--json` errors (human errors show the same effect/correlation) with exact valid correlation and effect/outcome/sync/logical bytes. Invalid selection/cursor and readonly policy exit 2; `not_found` exits 3; `store_error`, `store_locked`, `snapshot_unavailable` exit 4. `cleanup_conflict`, `cleanup_protected`, `snapshot_changed`, `cleanup_canceled`, `cleanup_commit_uncertain` and `cleanup_outcome_uncertain` exit 1. These describe retention, never send outcomes. Prior confirmed absence is successful `already_absent_unknown`, zero removed bytes, no new FULL write. An uncertain commit can have advanced `updated_at` while bytes remain; it never authorizes unlink. Broken stdout is `cleanup_outcome_uncertain`, retaining known effect/sync/bytes when a result reached this process. A lost IPC reply has unknown effect and nullable bytes. Preview afterward remains a catalogue observation: absence never manufactures a tombstone, removal event or proof of a past successful operation.

Existing schema constraints remain unchanged: revisions reference their draft, and the draft/head composite FK is deferred; outbound operations use an immediate composite `(draft_id,revision_id)` FK to retained revisions; immutable revision/outbound binding triggers forbid removing or rewriting that evidence. Reservation requires the draft to be active in code and in its insert trigger. Thus a normal discarded draft cannot gain a new reservation, while duplicate keys retain their original bindings. Cleanup modifies only `drafts.updated_at` and the one verified file; it neither deletes metadata nor evades those triggers. Validation used synthetic Linux plain/FTS fixtures, injected filesystem/commit/restoration failures and disconnected owners, with no live WhatsApp data.

Filesystem and DB do not share a transaction. FULL and directory sync request durability under SQLite/OS/filesystem assumptions, not against archive restoration or hardware that ignores flush; Windows lacks directory sync. Portable APIs have no atomic compare-inode-and-unlink: `os.Root` confines access, but external noncooperating path/content replacement can race the final check. Retained revisions continue exposing historical metadata and their expected snapshot location even after explicit byte removal; show/list do not certify availability or infer a cleanup event from absence.

## Writes, IPC and errors

Reads use the existing readonly archive opener without LOCK, migrations, permission normalization or media reads. An old archive needs an explicit writable upgrade. SQLite active-WAL bookkeeping retains the existing store limitations.

Create/update/discard reject `--read-only` / `WACLI_READONLY=1` (exit 2) before store/delegation effects. Writes hold the existing store LOCK; only an `ErrLocked` attempts delegation to the existing sync owner's socket/serialized slot. The local handler neither accesses WAClient nor consumes/updates send pacing. One deadline covers queueing and local work. It rechecks CAS, fixed store scope, own account for preparation, media roots and input bounds.

Pre-generated IDs and a versioned complete-request hash correlate IPC results; returned canonical payload/hash are revalidated. They are not dedupe/replay keys. Partial encoding, lost/decode-failed replies, old untyped owners, ID/hash mismatch, uncertain DB commit and stdout failures after mutation return `local_write_uncertain` (exit 1), with typed draft/revision IDs when available. Never automatically replay or fall back to a second writer after dispatch. Inspect the exact IDs in the selected archive. A typed owner refusal can describe a local no-write policy/conflict/error, but cannot claim rollback of a published snapshot.

Errors are sanitized and remain operation-specific: usage/read-only/invalid cursor exit 2; not found exit 3; archive/identity/document availability exit 4; CAS conflict/known pre-dispatch deadline/uncertain exit 1. Malformed, noncanonical, unsupported-version, hash/identity-mismatched or incompatible persisted payload/review data use a sanitized store error with exit 4 for show/discard, preserving the internal cause; caller ID/input/cursor validation remains exit 2. Optional `error.draft` contains only draft/revision/hash correlation and is absent from unrelated commands. Owner IPC now applies the shared inclusive 4 MiB encoded-input limit before buffering/decoding, counting leading whitespace and the first JSON value with at most one extra byte read for overflow detection. This intentionally refuses excessive legacy envelopes that were previously unlimited; it does not bound process RSS. The canonical internal draft request retains its 256 KiB + 16 KiB limit, including JSON escaping, and draft response reads remain capped. The outer draft decoder keeps its existing unknown/duplicate/trailing-field semantics within the shared limit; cleanup retains its smaller canonical newline frames. Document snapshot bytes (up to 100 MiB) are streamed separately and never embedded in the IPC request. See [sending](send.md) for the common input boundary.

The outbound integration adds explicit `outbound send` and retains readonly show/list. Retained operations reference exact immutable revisions, including explicitly selected older revisions of an active draft, and never follow a mutable head.

## Immutable voice PTT

`draft create/update --voice PATH` selects a typed voice revision. It fixes `AudioMessage.PTT=true` and MIME `audio/ogg; codecs=opus` from validated bytes, independently of the extension. The original bytes, tags, input-rate metadata, output gain and pre-skip are preserved. There is no generic audio kind, automatic detection into another draft kind, MIME override, document disguise or legacy fallback. The existing frozen textual quote rules apply. The source path is transient input; it is not retained or reopened for dispatch.

The supported profile is intentionally narrower than general Ogg/Opus. It requires Ogg structure version 0; one complete logical stream with sequence 0 onward, one initial BOS and final EOS; a standalone exact 19-byte OpusHead version 1 with mapping family 0 and one or two output channels; bounded OpusTags ending its own page; normal Opus packet framing codes 0–3; and a zero-origin declared timeline. Cropped/joined streams, chains, multiplexing, other mappings/versions, empty pages and multistream framing are outside this profile. Some broader formats are valid Ogg/Opus; profile refusal does not assert universal corruption.

Every page CRC, lacing table, continuation boundary, packet size and remaining byte count is checked. Tags and audio may span pages, including a terminating zero lacing segment after an exact multiple of 255 bytes. Missing/truncated headers/tags/pages/packets, serial/sequence gaps, invalid flags, inconsistent granules and bytes after EOS are rejected. Completed header granules are zero; incomplete pages use the absent-granule sentinel. Nonfinal completed audio granules equal accumulated packet durations at 48 kHz, independently of the input sample rate/channel count. Final trim is confined to the last packet and leaves positive samples after pre-skip. Compressed frame bodies are opaque: this checks declared structure and framing, not successful decoding, intelligibility or audio quality. Zero-length PLC/DTX frames may be structurally legal and contain no speech.

Local quotas are 100 MiB file bytes and 256 KiB canonical payload; 64 KiB for the entire Tags packet; 61,440 bytes per audio packet; 1,000,000 pages; 1,440,000 audio packets; and 172,800,000 encoded samples at 48 kHz (one hour, including pre-skip/final trim). These are local preparation limits, **not WhatsApp limits or a process RSS guarantee**. Frame lengths are bounded at 1,275 bytes and packet duration at 120 ms. Lengths/counts/rates/granules never authorize unbounded allocation. No decoder, ffmpeg dependency, STT or provider is involved.

Payload v1 freezes MIME/size/digest, Opus header metadata, encoded samples and declared playable samples. All preexisting variants retain their exact canonical JSON/hash. PTT is implied by the voice kind; seconds and waveform are always absent from the protobuf in this increment, even when the declared timeline can be calculated. Previews show `basis=declared_structure`, PTT and optional-field absence, structural metadata and verification-at-creation time. They expose no vendor/comments, bytes, base64, transcript or human approval. Full detail adds only the managed path derived from revision ID. Show/list do not open/stat the media; creation metadata is not proof of current integrity or decoded duration. Inspect bytes separately with appropriate local tools.

Create/update voice input uses **request v3 only**, with its own path field and empty legacy File. v1/v2 with voice and v3 without exactly voice create/update fail before source/store/network. Image retains its v2 contract; outer/outbound IPC remain v1. Upgrade the owner with the CLI. Real pre-voice owners reject the typed input and cannot reinterpret it as legacy file/voice; an uncorrelated old refusal can appear as `local_write_uncertain`. Unknown/mismatched/lost replies are uncertain without downgrade/replay. Older clients reject `--voice`; older owners cannot dispatch a stored voice revision.

Structural invalidity, unsupported profile and inspector/file quota refusals use sanitized `invalid_arguments` exit 2. The same optional owner advice distinguishes these categories only for a valid, correlated voice v3 request. Missing/unknown advice retains the recognized base error; mismatched envelopes/hash/IDs remain uncertain. `voice.canceled` advice applies only to structural validation canceled **before publication or revision persistence**. Copy/queue/transport timeout, lost replies, unknown publication and cancellation after effects never become this argument refusal; consult local state without replay. Published or unknown snapshot artifacts remain retained; a voice snapshot failure after publication reports `local_write_uncertain`.

Dispatch uses the existing reservation/executor: size/digest verification and a second structural pass compare all frozen metadata on the exact upload buffer before connection/upload. No source reopen, decoding, normalization, conversion, waveform generation or external probe occurs. Upload uses MediaAudio and the existing protobuf/SDK encoder with PTT=true and the frozen quote. Idempotency, SDK same-ID retries, zero application resend, ACK/history warnings and certainty rules stay unchanged.

History stores existing audio media fields and quote references, with no invented caption/transcription. The message schema has no new PTT column; generic historical audio cannot retrospectively prove voice kind. Correlated own/history raw AudioMessage echoes with PTT=true can confirm a voice operation; false/nil PTT, edits and unmatched identity/chat/ID cannot. Played/unknown receipts do not promote delivery/read. Voice snapshots are retained after update/discard and remain explicit `non_document` in document cleanup; no new GC/delete mode exists. Fixtures establish offline behavior only; real WhatsApp compatibility remains pending separately authorized QA.
